# Po0 解锁助手

Po0 解锁助手通过国外出口 VPS，为受公网访问限制的国内入口提供可回滚的管理出站能力，并可让指定的 systemd Agent 使用国外出口。

它不会修改两台 VPS 的默认路由、MTU 或 sysctl，也不会自动代理全部服务。国外出口代理、反向隧道端口和国内入口本地代理均只监听回环地址。

对于使用自动发现的 Komari Agent，助手会在服务启动前验证现有 `auto-discovery.json` 是否仍被面板接受。只有文件损坏或面板明确返回 Komari 的未授权响应时，才把旧身份隔离备份并允许 Agent 重新注册；网络、TLS、代理或服务器临时故障不会触发重置。自动发现密钥与客户端令牌不会写入助手配置或命令行。

对于面板端口被国内服务商封禁的 ForwardX，Agent 扫描会在用户明确选择并再次确认后，为 `forwardx-agent.service` 启用专用 HTTP/HTTPS 控制面代理。该配置不注入 `ALL_PROXY`，不会主动把 ForwardX 的原始 TCP 转发数据面整体改道；启用、刷新、停用和完整回滚仍由助手统一管理。

对于已确认兼容的官方 Go 版 CF Probe v1.0.0 至 v1.0.6，助手会保留已有的安全自定义测速目标，只把缺少端口或命中当前封禁端口的目标改为经过连通性验证的国内直连 TCP 53 目标，避免 Agent 默认探测 80 端口而长期没有延迟。默认四项目标使用金华三所高校官方域名公开发布的权威 DNS，不会使用可能改落入口附近的 Anycast；目标改写带有失败回滚与停用恢复记录。面板在启动或后续设置变化时若重新覆盖目标，服务专用守卫会保留面板的新配置版本和其他字段，只恢复四项测速目标并重启一次 Agent。快照版或未知 Go 修订版不会被强行修改。Go 版的面板上报仍经国外出口，因此这项处理只修复延迟，不改变面板识别到的来源地区。

功能 4 重新选择已经由助手配置的 Agent 时，可以检查并更新当前出口配置，或只撤销该服务的国外出口。撤销不会卸载 Agent；它会恢复直接联网，并在服务无法恢复运行时自动回滚。

## 普通使用

每个 v2 Release 只提供一个正式脚本：

```text
po0-unlock-v2.sh  公开版
```

公开版保留代理、隧道、Agent 管理、健康检查、完整回滚、在线更新和上一版助手恢复等全部功能。它从预期的公开 GitHub Release 匿名检查并安装脚本更新，不要求、读取或保存 GitHub Token。

将脚本保存为国外出口 VPS 的 `/root/po0-unlock.sh`，然后以 root 运行：

```bash
bash /root/po0-unlock.sh
```

首次部署完成后，助手会正式安装到 `/usr/local/sbin/po0-unlock`，并创建 `po0` 快捷命令；长期连接配置保存在 `/etc/po0-unlock/hosts.conf`。以后直接运行 `po0` 完成连接信息更新、状态检查、Agent 扫描、回滚和匿名在线更新。`/root/po0-unlock.sh` 只是首次安装或本地升级的候选文件，操作完成后可以删除。详细操作见 [使用说明.md](./使用说明.md)。

连接配置优先使用国内入口的服务商私网 IPv4。如果国外出口没有可用于该私网路径的本机私网地址，助手会请求填写国内入口公网 IPv4，然后按实际路由自动绑定国外出口源地址，不再直接退出。

更新现有连接时，新地址会先在内存中准备并展示；确认前不会改写 `/etc/po0-unlock/hosts.conf`。授权失败或新反向隧道尚未稳定时，助手会恢复原连接配置；新隧道确认稳定后，新配置会立即成为正式状态，后续 Agent 刷新或最终状态检查即使失败也不会把配置倒退成旧地址。若旧配置自动恢复失败，事务备份会保留并显示准确路径。

首次授权或连接地址变化时，SSH 会使用 `/root/.ssh/po0-unlock-admin.known_hosts` 进行严格主机密钥校验，并显示主机指纹。请先与服务商控制台提供的指纹核对，再确认继续；无法确认时直接取消。没有可信主机密钥记录时，脚本不会发送密码或执行国内入口命令。

升级时会安全复用旧版留下的 root 专用 `0600` 管理公钥；新生成的公钥仍使用 `0644`。匹配只依据算法与密钥数据，不受不同 OpenSSH 版本附带的公钥注释影响。两种权限都不可由普通用户写入，符号链接、额外硬链接、属主异常或更宽松权限仍会被拒绝。

一个正在使用的国内入口只允许归属一套国外出口部署。新出口机首次安装时，会先在授权写入前只读检查国内入口，再在上传组件前复核；如果发现已有 `ACTIVE` 安装状态，会停止并要求改用独立入口测试机，不会添加新管理密钥、更新组件或回滚现有 Agent。首次安装的失败清理还必须匹配本次随机事务标识，并发安装也不能回滚另一套部署。

如果更新连接时发现国内入口已经重装，导致已有主机密钥与当前密钥不一致，脚本会进入显式的“服务器重装后的 SSH 指纹恢复”向导：自动读取当前 `ed25519` 指纹，同时显示旧指纹和新指纹；新指纹只是网络扫描得到的候选值，只有你先通过服务商控制台确认确实重装或更换，再输入精确的 `REPLACE` 才会替换记录。`--yes` 也不能跳过这一步，输入 `0`、其他内容或遇到 EOF 都会保留旧记录；替换前的 `known_hosts` 会以 0600 权限备份并显示路径。正常情况下无需手工执行 `ssh-keygen -R`。

反向隧道等待两个国内入口回环监听就绪时，也只使用隧道专用主机密钥记录，不读取系统全局 `known_hosts`。

同一次操作中的国内入口 SSH 命令和组件上传会复用一条临时控制连接，减少公网路径上的重复握手。首次控制连接如遇链路抖动会进行最多 3 次有限重试；远程命令本身不会自动重放。

助手会在确认已安装的国内入口组件与当前内嵌版本逐字节一致且权限安全后直接复用，避免健康检查、最终状态检查和 Agent 扫描重复上传。连接更新会显示四个内部阶段及耗时，健康检查与 Agent 扫描也会显示准备和执行进度。

国内入口正式组件更新前会检查既有目标的普通文件属性、root 属主、`0700` 权限和单一硬链接；发现符号链接、异常硬链接或属性错误时会停止并保留原文件。新组件写入后还会复核这些属性、SHA-256 和 Shell 语法。

安装、连接更新、健康检查、Agent 扫描和回滚共用 `/run/po0-unlock/operation.lock` 互斥锁；已有 Po0 操作进行时，新的进程会立即返回，不会建立 SSH 会话或执行远端命令。操作锁目录和文件必须由 root 独占，符号链接或异常硬链接会被拒绝。

正式国内入口组件调用按工作量设置 15 至 300 秒的独立上限；只读调用超时时会明确说明本次调用没有修改入口，安装、刷新或回滚阶段超时则会提示可能已有部分修改，并要求执行完整回滚。国内入口写配置前最多等待写锁 30 秒，超时后绝不会在无锁状态下继续；若发生在回滚期间，应在锁释放后重新运行完整回滚。

Agent 扫描的 systemd 服务列表和每个服务的元数据读取都有超时上限；国内入口执行扫描组件的总时间最多约 60 秒，交互选择期间保持终端前台，输入不会被超时包装吞掉。缺少 `timeout` 或读取异常时只结束本次扫描，不会继续改动 Agent。

反向隧道确认新连接稳定后，连接地址、端口和生效时间会作为一个事务整体提交；写入中途失败会恢复旧记录，进程中断时会保留事务备份供人工处理，不会继续假定状态已经完整更新。

国外出口的安装标记、隧道配置、主机密钥、代理配置和回滚目标会统一检查 root 属主、预期权限、普通文件类型和单一硬链接；符号链接、悬空链接或异常硬链接会被拒绝，健康检查、连接重配置和回滚不会跟随外部路径。新建隧道密钥固定为私钥 `0600`、公钥 `0644`；完整回滚也能安全清理旧版严格 umask 留下的 root 专用 `0600` 公钥，不会因此形成半回滚状态。

Agent 扫描会先快速列出候选服务；只查看或取消时不会验证公网。只有确认要修改服务后，才会并行验证 HTTP 与 SOCKS5 国外出口，两项都通过后才会重启并配置该 Agent。

选择 CF Probe 时，Agent 扫描会再问一次出站方式：默认只注入代理环境变量；另一种在此基础上额外加一条本地转发，供那些不读代理设置、自己直接连面板的实时通道使用（典型症状是面板上一直显示在线，但实时数据从来没上来过）。转发所需的文件与服务由助手统一托管，撤销国外出口或完整回滚时会一并拆除，健康检查也会核对它是否仍在运行、以及重启后会不会自动起来。已经配置过的 CF Probe 可以在管理菜单里切换出站方式。

脱敏诊断报告会额外记录连接配置读取、两端概况、完整健康检查和近期错误采集的阶段耗时，并汇总本次操作实际发生的国内入口 SSH 初始建连次数。国外出口当前隧道配置的生效时间只会从受保护的安装状态读取，无法安全验证时显示“未知”。

`po0 check` 提供健康检查结论的非交互只读入口，供定时巡检通过 SSH 调用：不需要终端，不画菜单，不询问修复，也不建立恢复点。退出码 `0/1/2/3` 分别表示正常、提醒、异常和检查本身失败；`--json` 输出单行结构化结果，每项说明沿用诊断报告的脱敏规则。它不参与已安装脚本的接管流程，从候选副本运行也不会改动现有安装。

## 公开版：从公开 Release 匿名更新

公开版不使用 GitHub Token。在国外出口 VPS 运行 `po0`，选择 `6) 脚本更新与恢复`，再选择“检查并更新脚本”即可。更新器仅通过 HTTPS 查询预期的公开仓库，只接受最新的正式、非预发布 Release，并校验仓库身份与公开属性、Release 标签、脚本内版本、GitHub 附件 digest、Shell 语法和内置自检。通过全部检查并取得确认后，它才会备份当前脚本并原子替换。

### 从旧私有版或旧分享版接管

旧私有版不会自动改用新公开仓库，旧分享版也没有在线更新入口。请从公开 Release 手动下载更高版本的 `po0-unlock-v2.sh` 和 `po0-unlock-v2.sh.sha256`，在可信设备上核对 SHA-256，上传到国外出口后以 root 直接运行。候选脚本会安全接管到 `/usr/local/sbin/po0-unlock`；失败会恢复旧脚本，不修改代理、隧道、Agent 或连接配置。详细命令和检查顺序见 [使用说明.md](./使用说明.md)。

确认已安装版本显示预期的更高版本和“公开版”后，如果原来使用旧私有版，请手工删除旧令牌文件 `/var/lib/po0-unlock/updater/github-token`，并在 GitHub 网页撤销对应 Token。公开版不会读取、上传或自动删除这个历史凭据。

v2 不支持从 v1 原地升级。v1 Release 使用 `po0-unlock.sh` 资产，v2 Release 使用 `po0-unlock-v2.sh` 资产；两条更新通道互不兼容。部署 v2 前必须先使用最后一个 v1 正式版完成完整回滚，再在清理后的环境中全新安装。

### “恢复上一版助手”与“完整回滚”不要混淆

| 菜单 | 用途 | 是否改变现有代理、隧道或 Agent |
| --- | --- | --- |
| `6) 脚本更新与恢复 → 2) 恢复上一版助手（不改服务）` | 恢复在线更新前保存的正式助手脚本 | 否 |
| `5) 完整回滚` | 撤销国内入口的业务部署并恢复配置 | 是 |

“恢复上一版助手”只管理脚本文件，不会重启或改动现有服务；菜单 5 才会停止隧道、移除国内入口代理配置和受限账户，并恢复国外出口组件。完整回滚确认界面可输入 `0` 安全返回主菜单，服务器不会被修改。真正清理国外出口配置和密钥前，助手会确认反向隧道与国外出口代理都已停止；任一停用失败、状态无法确认或服务仍在运行时会立即中止，保留全部材料和安装状态，修正 systemd 问题后可直接重试完整回滚。

正常脚本更新与恢复产生的脚本备份最多保留最近 3 份，其中当前可由菜单恢复的备份始终保留。开发测试使用的人工候选和人工备份不属于普通用户更新流程，助手不会自动删除。

## 仓库结构

- `setup.sh`：国外出口主控与交互菜单源码。
- `overseas-exit-role.sh`：国外出口代理、隧道和回滚逻辑。
- `src/cn-entry-role/`：国内入口出站、Agent 管理和回滚逻辑的开发模块。
- `cn-entry-role.sh`：由国内入口模块确定性生成的组件产物。
- `tools/build-cn-entry-role.sh`：按固定顺序生成或检查国内入口组件。
- `tools/build-single-file.sh`：把三个源码组件确定性构建为单文件。
- `po0-unlock.sh`：公开版生成产物。
- `tests/update-acceptance.sh`：公开 Release 匿名更新、上一版助手恢复和完整回滚交互的离线验收测试。
- `tests/install-entry-acceptance.sh`：正式系统入口、`po0` 快捷命令、旧部署迁移与冲突保护测试。
- `tests/config-migration-acceptance.sh`：连接配置目录迁移、冲突保护、权限边界与旧版回退测试。
- `tests/cf-probe-acceptance.sh`：CF Probe Shell/Go 延迟兼容、面板动态配置守卫、旧 Shell 真实地区上报、失败回退和清理回滚测试。
- `tests/komari-acceptance.sh`：Komari 旧延迟方案清理、自动发现身份守卫、脱敏与漂移保护测试。
- `tests/health-acceptance.sh`：一键健康检查的只读边界、覆盖范围、安全修复确认和失败回滚测试。
- `tests/diagnostic-acceptance.sh`：脱敏诊断报告的只读边界、本地保存、文件保护、内容隐藏、阶段耗时和安全状态读取测试。
- `.github/workflows/ci-release.yml`：持续集成与标签发布流程。
- `使用说明.md`：中文用户手册。
- `CHANGELOG.md`：各版本相对上一正式版的增量变化。

`setup.sh`、`overseas-exit-role.sh` 和 `src/cn-entry-role/` 是开发源码；不要手工编辑 `cn-entry-role.sh` 或 `po0-unlock.sh`。修改国内入口模块后，必须重新生成公开版单文件。

## 构建

不传版本号时，构建器使用当前默认版本；发布新版本时应显式传入新的语义化版本号：

```bash
bash tools/build-single-file.sh 2.0.0
```

也可以只检查已提交的国内入口组件是否与模块完全一致：

```bash
bash tools/build-cn-entry-role.sh --check
```

构建器会校验模块生成结果、源码语法、内嵌组件哈希、自检与逐字节一致性，并在替换发行文件前把上一版本保存到仓库相邻的备份目录。

## 本地验收

```bash
bash -n setup.sh
bash -n overseas-exit-role.sh
bash -n cn-entry-role.sh
bash -n tools/build-cn-entry-role.sh
bash -n tools/build-single-file.sh
bash -n po0-unlock.sh
bash tools/build-cn-entry-role.sh --check
bash po0-unlock.sh self-test
bash tests/update-acceptance.sh
bash tests/install-entry-acceptance.sh
bash tests/config-migration-acceptance.sh
bash tests/cf-probe-acceptance.sh
bash tests/komari-acceptance.sh
bash tests/health-acceptance.sh
bash tests/diagnostic-acceptance.sh

cmp -s <(bash po0-unlock.sh __extract-role overseas-exit) overseas-exit-role.sh
cmp -s <(bash po0-unlock.sh __extract-role cn-entry) cn-entry-role.sh
```

正式部署仍应遵循：上传为候选文件、核对 SHA-256、执行服务器端自检、备份旧版、原子替换、只读检查状态。不要直接在生产服务器上测试完整回滚。

## CI 与发布

推送到 `main` 或提交 Pull Request 时，GitHub Actions 会执行国内入口模块一致性检查、公开版语法和单文件自检、内嵌角色一致性、确定性重建，以及系统入口、配置迁移、匿名更新、CF Probe、Komari、健康检查和诊断报告离线验收。

推送严格的 `vX.Y.Z` 标签时，工作流还会确认标签等于公开版单文件内声明的版本。全部检查通过后，发布作业会先创建草稿 Release，上传脚本与 SHA-256 两个附件，再把 GitHub 返回的每个附件 digest 与本地 SHA-256 逐一比对；只有数量、名称和摘要全部一致才转为正式 Release：

- `po0-unlock-v2.sh`
- `po0-unlock-v2.sh.sha256`

发布前必须先用相同版本号重新构建并提交生成产物。例如发布 v2.5.1：

```bash
bash tools/build-single-file.sh 2.5.1
bash po0-unlock.sh self-test
bash tests/update-acceptance.sh
bash tests/install-entry-acceptance.sh
bash tests/config-migration-acceptance.sh
bash tests/cf-probe-acceptance.sh
bash tests/komari-acceptance.sh
git diff --exit-code -- po0-unlock.sh
git tag v2.5.1
git push origin v2.5.1
```

标签与脚本版本不一致、生成产物不能由源码确定性重建，或任一验收测试失败时，Release 不会发布。同标签 Release 已存在时直接拒绝；草稿上传或 digest 校验失败时，工作流会清理本次创建且尚未发布的草稿。任何修订都必须提升版本号并创建新标签。Actions 默认仅有仓库读权限，只有标签发布作业取得 `contents: write`；第三方 Action 必须固定到完整提交 SHA。

## 安全规则

- 永远不要提交 `hosts.conf`；它可能包含真实私网/公网连接地址和 SSH 端口。
- 不要提交密码、令牌、SSH 密钥、known_hosts、节点配置、面板地址或服务器备份。
- 不要在公开讨论、提交信息或发布说明中填写真实服务器地址、端口或凭据。
- 首次初始化会拒绝状态文件、隧道密钥、管理密钥或国内入口托管目标上的符号链接和异常权限；请先人工确认并移走异常路径，不要强行覆盖。
